# M7 — Admin Web (Codes, Organizers, Flags, DUPR Verify, Stats)
**Date:** 2026-07-24
**Milestone:** M7 (Phase 1 Milestone Order, spec §10) → web deploy
**Spec:** `docs/2026-07-24-picklepro-ph-mvp-spec.md` §6, §9
**Depends on:** M1 (schema/RLS — every admin capability here rides on the
`is_admin()` policies shipped then)
**Status:** Executed

## Scope (spec §6, architecture per §9)

`admin-web/` — Vite + React + TypeScript + Tailwind, Supabase JS client,
React Router with an admin route guard, TanStack Table for data tables,
client-side CSV export. Deploy target: Vercel (static build).

1. **Auth** — Supabase email+password sign-in; after session, the guard
   fetches the user's own `profiles` row and requires `role = 'admin'`.
2. **Activation Codes** — generate single or batch (auto 12-char codes,
   ambiguity-free alphabet), price label (₱) / note / free flag; status
   flow Generated → Sent → Redeemed (redeemer + timestamp shown); revoke
   unredeemed; copy a code; export the table as CSV client-side.
3. **Organizers** — every `role='organizer'` profile with tournaments
   count and codes-redeemed count; suspend / reactivate.
4. **Sandbag Review Queue** — open flags with player, division, reason and
   the evidence JSON; actions: dismiss, or set a rating override (writes
   `ratings.override` for the division's event type) + admin note →
   status `actioned`.
5. **DUPR Verifications** — profiles with a DUPR id + proof screenshot and
   `dupr_verified = false`; view proof, verify (sets `dupr_verified`) or
   reject (clears the proof URL so it leaves the queue; id/rating stay,
   unverified).
6. **Stats** — totals: players, organizers, tournaments, matches, codes
   sold (non-free, sent or redeemed) vs redeemed.

## Notes / decisions
- **Admin gate = `profiles.role`, not a client email allowlist.** Spec §6.1
  says "email allowlist", but the backend's actual enforcement (M1 RLS,
  `is_admin()`) is role-based — every admin read/write in this app is
  *already* rejected by Postgres for non-admins. A client-side email list
  would be a second, weaker source of truth that can drift; the guard
  instead mirrors what RLS enforces. Making someone admin = setting their
  profile role (service role / SQL), which doubles as the allowlist.
- **"Restrict from tiers" (spec §6.4's third action) is deferred.** The M1
  schema has no tier-restriction field on profiles/ratings — it belongs to
  the P3 full sandbag engine (spec §11). Dismiss + rating override + note
  are implemented; noted here rather than silently dropped.
- **Code generation is client-side** (crypto.getRandomValues, 12 chars,
  no 0/O/1/I) inserted directly — RLS gives admins full CRUD on
  `activation_codes`; no Edge Function needed for creation, only
  redemption (which stays server-side per M1).
- **This milestone is actually compiled**: Node is available in this
  environment (unlike the Android SDK), so `tsc --noEmit` and
  `vite build` both run as part of verification.
- Deploying to Vercel needs `VITE_SUPABASE_URL` + `VITE_SUPABASE_ANON_KEY`
  env vars; see `admin-web/.env.example`.
